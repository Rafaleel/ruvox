# Ruvox: project plan (Phases 0 to 4)

Audience: the coding agent that implements this (Codex), plus the owner. Read `AGENTS.md` first, then this file, then `.ai/HANDOFF.md`.
Language of everything in the repo: English. Only the product UI and exercise content are in Brazilian Portuguese (pt-BR).

## 1. Product

Ruvox ("ru" + "vox", voice) is a **local-first desktop app** that teaches Russian to Brazilian Portuguese speakers, starting from the Cyrillic alphabet.

- Exercises are generated by AI agents (Agno), adapt to the learner's mistakes, and can use vocabulary from song lyrics the learner pastes in.
- UI entirely in pt-BR. Russian content shows an approximate pronunciation for Brazilians, e.g. `Привет (pri-VIÉT)`.
- Runs on the owner's machine: a Tauri window, a local Python backend, a local SQLite file. Nothing is hosted.
- Also usable from the owner's phone over the local Wi-Fi while the desktop app is running (opt-in, Phase 4). Native phone apps are out of scope.
- Short sessions (5 to 10 minutes) with score and progress.
- Game modes 1 to 3 (and 4 to 6 once content exists) must work with **no LLM and no API key**. LLM features degrade to a deterministic fallback when the API is down, unconfigured, or too slow.
- The app ships **no song lyrics**. Lyrics live only in the user's local database. Exercises use single words and short excerpts.

## 2. Architecture decisions (fixed; do not re-litigate)

| # | Decision | Reason |
|---|----------|--------|
| D1 | Monorepo: `backend/` (Python), `frontend/` (Vite SPA), `src-tauri/` (Rust shell), `docs/`. | One repo, three small parts. |
| D2 | Backend: Python 3.12, FastAPI, Pydantic v2, SQLModel on SQLite, Alembic migrations, `uv`. Agno for agents from Phase 2. | Agno is Python; users keep data across versions, so migrations from day one. |
| D3 | Frontend: Vite + React + TypeScript + Tailwind + React Router + TanStack Query. Built as a static SPA. No Next.js. | Tauri needs a static frontend; Next.js adds nothing without a server. |
| D4 | The backend **serves the built frontend** at `/` (SPA fallback to `index.html`) and the API under `/api`. | The Tauri window and the phone load the exact same URL. |
| D5 | Tauri 2 shell starts the backend as a **sidecar** and opens a window on it. Dev: spawns `uv run`. Release: bundled PyInstaller binary. | Thin shell, no rewrite. |
| D6 | Sidecar handshake: the backend binds `127.0.0.1` on the port given by `--port` (default `0` = any free port; dev uses `--port 8000`), then prints one line `RUVOX_READY port=<n>` on stdout. Tauri reads it, then opens `http://127.0.0.1:<n>/`. The backend exits when its stdin closes (no orphans). | Free port, no race, no orphan processes. |
| D7 | The Tauri window is created in Rust after the handshake. `tauri.conf.json` has no static windows; `frontendDist` points to a tiny `src-tauri/splash/` page shown while the backend starts. | The URL is only known at runtime. |
| D8 | All data lives in the OS user data dir (`platformdirs`, app name `ruvox`), overridable with `RUVOX_DATA_DIR`. Never in the repo. | Local-first, safe upgrades. |
| D9 | The API key and model live in `<data dir>/config.json` (file mode 0600), editable from the Settings screen. `ANTHROPIC_API_KEY` env var overrides. | Simplest secure-enough option for a single-user local app. |
| D10 | Types flow backend to frontend: FastAPI OpenAPI schema generates `frontend/src/api/schema.d.ts` with `openapi-typescript`. The frontend never parses free text. | One source of truth. |
| D11 | Agent outputs are structured (Pydantic models; the exact Agno parameter name is fixed in ADR 0004). Python validators check the content after the model call. On failure: retry once, then fall back to the no-LLM path. | The LLM is never trusted blindly. |
| D12 | The spaced-repetition (SRS) service is the only writer of `ReviewState`. Agents may select and order among candidates the SRS service provides; they never create or change schedules. | An agent cannot corrupt a learner's schedule. |
| D13 | User memory is our own tables (`UserProfile`, `ReviewState`, `Attempt`), not Agno's memory. Summaries are passed into prompts. | Testable, local, easy to inspect. |
| D14 | Single user per install, but all tables keep `user_id` (default user id 1, created on first run). | Matches the spec and keeps a future option open. |
| D15 | Security: backend binds `127.0.0.1` only (until the Phase 4 LAN toggle); a Host-header allow-list (`localhost`, `127.0.0.1`, and the LAN IP when enabled) blocks DNS rebinding; no wildcard CORS. | Other local processes and web pages must not drive the API or spend the API key. |
| D16 | Target platform: Linux x86_64 first (owner runs Arch). Windows and macOS are best-effort later. | Scope. |
| D17 | Task runner: root `Makefile` (`make dev`, `make check`, `make build-sidecar`). | Present on every dev machine. |

## 3. Data model (SQLModel; names are fixed)

- `User(id, name, created_at)`
- `Item(id, kind[letter|word|expression], text, pronunciation, meaning, source[seed|song], group, difficulty, song_id?)`
- `Song(id, user_id, title, artist, text, created_at)`: lyrics pasted by the user, never bundled.
- `StudySession(id, user_id, mode, started_at, ended_at?, score)`. Do not name it `Session`: it clashes with `sqlmodel.Session`.
- `Question(id, session_id, type, prompt, options JSON, answer, explanation, item_ids JSON, input_kind[choice|text|flip|pairs])`
- `Attempt(id, user_id, question_id, answer, correct, grade 0-5, time_ms, created_at)`: validate `grade` in the service layer (SQLModel table models do not validate).
- `ReviewState(user_id, item_id, repetitions, interval_days, ease, next_review, last_grade)` with composite primary key `(user_id, item_id)`.
- Phase 2: `LLMCall(id, agent, model, input_tokens, output_tokens, latency_ms, cost_usd, ok, error, created_at)` and `UserProfile(user_id, level, weak_points JSON, preferences JSON, updated_at)`.

## 4. Core algorithms (specified so tests can pin them)

### Spaced repetition (simplified SM-2), `services/srs.py`, pure functions

Input: current state (`repetitions`, `interval_days`, `ease`) and `grade` 0 to 5.

- `grade < 3`: `repetitions = 0`, `interval_days = 1`, `ease` unchanged. The item is also requeued in the same session (at most 2 times).
- `grade >= 3`: `repetitions += 1`; interval is `1` on the first success, `6` on the second, then `round(previous_interval * ease)`.
- Ease update on every answer: `ease = max(1.3, ease + 0.1 - (5 - g) * (0.08 + (5 - g) * 0.02))`. Start ease: 2.5.
- `next_review = now + interval_days` (UTC; compare in UTC).

Grade mapping when no LLM is involved: correct in 5 s or less is 5, correct slower is 4, wrong is 1, flashcard "knew" is 4, "missed" is 1, pairs matched first try is 4 and with mistakes is 2. The Corrector agent (Phase 2) returns its own 0 to 5 grade for typed answers.

### Content selection (no LLM), `services/selection.py`

1. Take items with `next_review <= now`, most overdue first.
2. Fill the remaining slots with new items from unlocked content, in seed order.
3. Letter groups: group 1 is unlocked from the start. Group k+1 unlocks when at least 80% of group k's items have `repetitions >= 2`.
4. A word is eligible when **every letter in it** has `repetitions >= 1` (compute from the word's characters).
5. A session has 10 questions by default (`size` 5 to 20). New items per session: at most 5.

### Answer checking (no LLM), `services/answer_checker.py`

Normalize with `strip`, Unicode NFC, `casefold`, and `ё` to `е`. Correct means equal after normalization. Choice questions compare the option id/text exactly.

### Streak (Phase 4)

A day counts if at least one session with 5 or more answered questions was finished that local day. Streak is the number of consecutive counted days ending today, or ending yesterday if today has none yet.

### Mastery buckets (Phase 4)

`learning`: repetitions below 2. `familiar`: repetitions 2 or more and interval below 21 days. `mastered`: interval 21 days or more.

## 5. API (v1; Phase 1 unless noted)

All under `/api`. JSON only. Errors use `{"detail": ...}`.

- `GET /health` returns `{"status": "ok"}`.
- `GET /items?kind=letter|word|expression&source=seed|song` returns the item reference list.
- `POST /sessions` with `{mode: "mixed"|1|2|3|..., size}` returns `{session_id, questions: [QuestionOut]}`. `QuestionOut` never contains the answer.
- `POST /sessions/{id}/answers` with `{question_id, answer, time_ms}` returns `{correct, grade, correct_answer, explanation}`.
- `POST /sessions/{id}/finish` returns `{score, answered, correct, items_to_review}`.
- `GET /progress` returns `{due_count, groups: [{group, total, learned}], words_unlocked, ...}`.
- Phase 2: `GET/PUT /settings`, `POST /settings/test-llm`.
- Phase 3: `POST/GET/DELETE /songs`, `POST /songs/{id}/analyze`, `POST /songs/{id}/confirm`.
- Phase 4: `GET /stats`, `POST /backup/export`, `POST /backup/import`, `POST /data/reset`.

`QuestionOut` is a Pydantic model: `{id, type, prompt, input_kind, options?: [str], pairs?: [...], item_ids}`.

## 6. Game modes

| # | Mode | Phase | Needs LLM |
|---|------|-------|-----------|
| 1 | Letter to sound ("como se lê Ч?") | 1 | no |
| 2 | Sound to letter ("qual letra faz 'tch'?") | 1 | no |
| 3 | Word reading to meaning (cognates first: банан, метро, кофе) | 1 | no |
| 4 | Typing: shown pronunciation or meaning, user types Cyrillic (on-screen Cyrillic keyboard) | 2 | no (LLM only explains near misses) |
| 5 | Flashcards "sabia / errei" | 3 | no |
| 6 | Timed pairs | 3 | no |
| 7 | Cloze: fill the blank in a short sentence, including song vocabulary | 3 | optional |

Mode 4 moves to Phase 2 (the spec's acceptance for Phase 2 needs typed answers corrected).

## 7. Working rules for every task

### Git and GitHub: the owner's global rules (apply to Codex exactly as to Claude)

These are copied from the owner's global Claude instructions (`~/.claude/CLAUDE.md`, "Fluxo de git"), which Codex cannot read. Treat them as binding:

- Work on a **branch per part of the work** (`feat/...`, `fix/...`, `docs/...`, also `chore/`, `ci/`, `test/`, `refactor/`). **Never commit directly to `main`.** Small follow-up requests on the same part reuse the same branch; do not stack one branch per request.
- Make **small, frequent local commits** while developing (Conventional Commits in English, e.g. `feat(backend): add srs service`; each commit builds and passes lint).
- **Push, open a PR and merge only with the owner's explicit authorization**, after a whole section is ready and verified. In this plan, **one PLAN task (one PR) is one section**: when a task is done and verified, update `.ai/HANDOFF.md`, then stop and ask the owner to authorize push and PR. Do not start a dependent task until the owner has merged the one it depends on.
- When creating a **new repository**, always ask the owner whether it is private or public. Never assume.
- Write commits, PR titles and bodies, code comments, names and docs in the language the repo already uses: **English** here (confirmed by the owner). User-facing UI text is pt-BR. If unsure which language to use, ask before writing.

### Task rules

- One task = one branch = one PR = one GitHub issue. The branch is cut from an up-to-date `main`: `<type>/<short-description>`.
- Work tasks in order. Do not start a task before its dependencies are merged.
- PR under about 400 changed lines, excluding lockfiles and generated files. If a task needs more, split it and tell the owner. Use `.github/pull_request_template.md` and link the issue with `Closes #N`. Merges are squash merges, with a Conventional Commits message.
- Tests ship with the feature. Mock the LLM in every test. No network in tests.
- Before saying done, run `make check` (once it exists), or the equivalent gates listed in `AGENTS.md`.
- Never commit secrets, `.env`, `*.db`, `.ai/`, real song lyrics, or build output.
- Log cost and latency of every LLM call (Phase 2 onward).
- If two approaches are close, take the simpler one and record the decision in HANDOFF. Ask the owner only about things that are hard to undo.

Output `SessionPlan{entries: [{item_id, mode, reason}], difficulty, notes}`. Validator: every `item_id` came from the candidates; no more than `size` entries; otherwise retry once then use the Phase 1 selection (D11, D12).
- Prompt in `agents/prompts/planner.md`. Tests with `FakeModel`: valid plan, plan with an unknown id (falls back), timeout (falls back).

### P2-4 Generator agent
Branch `feat/generator-agent`. Depends on: P2-3.
- `AgentQuestionGenerator` implements `QuestionGenerator`. Input: the plan. Output `list[GeneratedQuestion]`. Validators: exactly N questions, no duplicate prompts, the answer is among the options, Russian text is Cyrillic, item ids valid, pt-BR explanations present. Retry once, then `SeedQuestionGenerator`.
- Tests: valid output, duplicate prompts rejected, answer-not-in-options rejected, fallback path.

### P2-5 Corrector agent and mode 4 (typing)
Branch `feat/corrector-typing`. Depends on: P2-1, P1-5.
- Backend: question type `typing` (`input_kind=text`). Answer flow: the deterministic checker runs first (case, `ё`/`е`); an exact normalized match returns grade 5 with **no LLM call**. Otherwise the Corrector agent returns `Correction{correct, grade 0-5, explanation_pt, normalized_answer}`; offline fallback is strict comparison (grade 1 on a miss, generic explanation).
- Frontend: typing question UI with an **on-screen Cyrillic keyboard** component (phones and desktops without a Russian layout), plus physical keyboard input.
- Tests: normalization cases, no-LLM path on exact match, near miss goes through the agent (fake), fallback grade, keyboard component renders the 33 letters.

### P2-6 Team, memory and orchestration
Branch `feat/session-team`. Depends on: P2-3, P2-4, P2-5.
- Agno `Team` (mode and API per ADR 0004) as `SessionTeam` facade used by `POST /sessions` when a key exists: planner then generator, with an overall 25 s budget, then fallback. The response includes `source: "ai" | "offline"`; the UI shows a small badge.
- After each session update `UserProfile` (level estimate, weak points = items with the most misses, preferences) from attempts; feed its summary to the planner.
- Tests: ai path, offline path, partial failure, profile update.

### P2-7 Live smoke and cost visibility
Branch `chore/live-smoke`. Depends on: P2-6.
- `scripts/live_smoke.py` (opt-in via `RUVOX_LIVE_LLM=1`, never in CI) runs planner, generator, corrector once against the real API and prints cost and latency. `docs/llm.md` explains logs, the pricing table, and how to switch models.

## 11. Phase 3: songs (milestone "Phase 3: songs")

**Acceptance:** the owner pastes a lyric, reviews the extracted vocabulary, saves it, and practices those words in modes 4 to 7.

### P3-1 Songs data, API and UI
Branch `feat/songs`. Depends on: P1-6.
- `POST/GET/DELETE /songs` (title, artist, text up to 20 000 characters; 413 above). Deleting a song deletes its items and their review states; the UI confirms in pt-BR. Screen `/songs`: list, paste form, delete.
- Tests use invented text only. **Never put real lyrics in the repo, fixtures or tests.**

### P3-2 Music agent
Branch `feat/music-agent`. Depends on: P3-1, P2-1.
- `POST /songs/{id}/analyze` returns `SongAnalysis{vocabulary, expressions, grammar}` without saving. Vocabulary entries: `text`, `lemma`, `pronunciation_pt`, `meaning_pt`, `part_of_speech`, `excerpt`. Validators: Cyrillic text; `excerpt` must be a substring of the lyric and at most 8 words (truncate or drop otherwise); at most 40 entries; dedupe against existing items by lemma (link instead of duplicate).
- `POST /songs/{id}/confirm` saves the user-selected entries as `Item(source=song, song_id)` and creates `ReviewState` rows. UI: review screen where each entry can be unticked before saving.
- The lyric is untrusted input: pass it inside a delimited block, give the agent no tools, and rely on schema validation (prompt-injection safe by construction). Add a test with a lyric that contains instructions.
- Offline fallback: analyze returns a 503 with a pt-BR message ("Análise de músicas precisa da chave da API"); the rest of the app is unaffected.

Branch `feat/song-focus`. Depends on: P3-2, P2-6.

### P3-4 Mode 5: flashcards

### P3-5 Mode 6: timed pairs
Branch `feat/mode-pairs`. Depends on: P1-7.

### P3-6 Mode 7: cloze
Branch `feat/mode-cloze`. Depends on: P3-2, P2-4.

## 13. Risks and mitigations

- **Agno under PyInstaller** may not freeze cleanly. Mitigation: P0-5 spike before any agent work; stop and report if it fails.
- **Alembic inside the frozen binary** needs its scripts bundled; covered in P0-5 acceptance.
- **Sidecar orphan processes** on crash. Mitigation: stdin-EOF watcher plus kill on exit (D6).
- **LLM output quality and hallucinated Russian.** Mitigation: validators (D11), pt-BR content review by the owner, seed content is hand-written.
- **LAN exposure of the API key.** Mitigation: off by default, pairing code, Host guard (D15, P4-2).
- **PWA on HTTP.** Mitigation: scope reduced in P4-4.
- **Song lyrics and copyright.** Mitigation: nothing bundled, excerpts capped at 8 words, no real lyrics in tests.
- **Branch protection** is unavailable for private repos on the free plan. The owner decides (public repo, Pro, or protection by convention).
